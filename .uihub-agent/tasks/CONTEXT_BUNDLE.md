# Context bundle contract — Phase 8

A context bundle is the answer to one question: **what is the minimal necessary
context for this task?** It is produced by `npm run agent:context -- "<task>"`.

```
npm run agent:context -- "Fix WebM template preview"
npm run agent:context -- --json "Fix a payment verification bug"
npm run agent:context -- --manifest .tmp/ctx.json --expand-steps 2 "Fix the auth middleware"
```

## The one rule everything else serves

**A file may appear in a bundle only if the bundle can say why it is there.**

That is the whole design. Everything below is machinery for producing and
proving that sentence.

## Fields

| Field | Meaning |
|---|---|
| `task` | The task text exactly as given. |
| `generatedAt` | ISO-8601. The only wall-clock value; every other field is deterministic. |
| `intent` | `{ intent, why }` — e.g. `FIX`, "2 intent verb(s) matched". |
| `categories` | Ordered strongest-first, from the 18-category matrix. `UNKNOWN` when nothing resolved. |
| `surface` | **Array** of `FRONTEND` / `BACKEND` / `MCP` / … derived from resolved evidence, not guessed from the wording. |
| `confidence` | `HIGH` / `MEDIUM` / `LOW` — **never** a number or percentage — plus a separate `confidenceWhy` string. |
| `featureCandidates` | `FEATURE_MAP` slugs the task resolved. |
| `indexes` | **Indexes queried**, in order — so the bundle says whether the context came from the symbol index or only from keywords. Empty only for `UNKNOWN`. |
| `entities` | Every resolved component, symbol, service, hook, route and explicit file, each with its own evidence string. |
| `files` | Ranked context files. Each has `path`, `score`, `priority` (P0–P5), `tier`, `role`, `feature`, `lines`, `why[]`, `matched`, and `addedByExpansion` / `expansionTrigger`. |
| `knowledge` | Documents to read first, in priority order, each with the reason it was chosen. |
| `dependencies` | Relationships behind the selected files, derived from `expansionLog` so it can never disagree with what was really used: `path`, `trigger`, `how[]`. |
| `protectedAreas` | Protected paths the task touches, with `tier` and the rule text. |
| `validation` | Commands that must pass before the work counts as done. |
| `expansionLog` | One entry per added file: `step`, `path`, `trigger`, `how[]`, `reason`. |
| `expansionCount` / `expansionSteps` | Files actually added, and the step budget allowed. |
| `stopReason` | Why expansion stopped. Never empty. |
| `sizePolicy` | Which budget applied and why: `relevanceBudget`, `relevanceBudgetBase`, `relevanceBudgetExplicit`, `evidence[]`, `expansionBudget`, `expansionSteps`, `safetyCeiling`, `safetyCeilingApplied`, `droppedByCeiling[]`, `maxRelevanceBudget`. |
| `efficiency` | `totalIndexedFiles`, `qualifiedCandidates`, `initialFiles`, `expandedFiles`, `filesSelected`, `selectionRatio`. |
| `emptyReason` | Set **instead of** an empty `files` list: `why`, `searchedTerms`, `note`. |
| `unknown` | Present only when `categories` is `[UNKNOWN]`: `why` and `suggestion[]`. |

A real file entry:

```json
{
  "path": "backend/src/routes/paymentRoutes.js",
  "score": 112,
  "priority": "P1",
  "tier": "NORMAL",
  "role": "ROUTE_CONFIG",
  "feature": "payment-routes",
  "lines": 33,
  "addedByExpansion": false,
  "expansionTrigger": null,
  "why": [
    "belongs to the resolved feature \"payment-routes\"",
    "the task word \"payment\" names a segment of this path",
    "sits in the PAYMENT source root backend/src/routes"
  ],
  "matched": null
}
```

The machine-readable shape lives in
`.uihub-agent/generated/CONTEXT_BUNDLE_SCHEMA.json`, generated by
`generate-index.mjs` and validated by `validateBundle()` — so the schema and the
builder cannot drift apart silently.

## Priorities

| Priority | Means | Typical evidence |
|---|---|---|
| P0 | The direct target | exact file path, exact component or symbol name |
| P1 | Direct dependency | feature ownership, import, API relationship, partial name match |
| P2 | Reachable | page renders it, route reaches it, rare path segment named |
| P3 | Background | category source root, protected dependency, shared service |
| P5 | Added by expansion | only ever admitted by one of the seven permitted triggers |

## The seven permitted expansion triggers

Expansion is a decision with a recorded reason, not a reflex. A file may be
added only for one of these:

1. `DIRECT_DEPENDENCY` — a file the task named imports this file
2. `RELEVANT_CONSUMER` — this file imports a file the task named
3. `SHARED_SERVICE` — at least two named files import this service
4. `API_DEPENDENCY` — an endpoint named in the task is handled here
5. `STATE_DEPENDENCY` — a context/store/provider shared by named files
6. `PROTECTED_RELATIONSHIP` — a protected path depends on this file
7. `TEST_DEPENDENCY` — a test imports a file the task named

Never, under any circumstance: the file is nearby, shares a name, is in the same
directory, or "looks relevant". Those are denied explicitly in
`expand-reasons.mjs` because a rule that exists only in prose gets forgotten.

## Honesty guarantees

These are asserted by `.uihub-agent/tests/context.test.mjs`, not merely intended:

- **Every file has at least one reason.** No unexplained entries.
- **An empty result explains itself.** `emptyReason` carries `why`,
  `searchedTerms[]` and `note`.
- **`emptyReason` and a non-empty file list never coexist.** Expansion can turn
  an empty result into a non-empty one, and a bundle cannot claim both.
- **No file contents, ever.** Only paths, names, priorities and reasons.
- **No secrets.** The serialized bundle is passed through `scanText()` before it
  is emitted; a finding aborts with exit code 3.
- **Deterministic.** Same task + same indexes ⇒ byte-identical bundle apart from
  `generatedAt`.
- **Stale indexes are refused.** `agent:context` exits 2 unless the pre-check
  passes, or `--allow-stale` is given.

## Context size policy

Context size is governed by three separately-named numbers. They used to be one
number (`maxFiles: 25`) described in prose as "no arbitrary cap", which meant the
code and the documentation disagreed. The policy lives in
`scripts/lib/context-size.mjs` and every bundle reports its own copy in
`sizePolicy`.

| Number | Value | What it is |
|---|---|---|
| **Relevance budget** | 25 baseline, evidence-raised to at most 40 | A soft target for what relevance alone selects. Derived per task, not a cap. |
| **Expansion budget** | 1 step × 10 files by default | Independent of the relevance budget, so "relevance wanted 35" and "expansion added 8" are never conflated. |
| **Safety ceiling** | 60 | A runaway guard only. Not a target, and nothing legitimate approaches it. |

The relevance budget grows only with evidence the context-size contract allows —
feature scope, validation requirements, protected relationships, and task
complexity — and it **shrinks** when the task names files, because the named set
is the subject. It never grows because more files happen to be available: a
larger repository, or a task that matched more candidates, does not earn a larger
context.

Passing `maxFiles` explicitly is a caller override. It is honoured verbatim and
disables growth, because an explicit number is already a decision.
`npm run agent:context -- --max-files 8` therefore means exactly 8, and omitting
the flag means the derived budget.

If the safety ceiling fires, `sizePolicy.safetyCeilingApplied` is `true` and
`droppedByCeiling[]` names every path removed. Truncation preserves the ordered
list, so what survives is the strongest evidence rather than an arbitrary prefix.
Across the ten canonical benchmark tasks it never fires.

## Reading the numbers honestly

`selectionRatio` is measured against the **repository** (501 indexed files), not
against the candidate list. An earlier version divided by the candidate count,
which made "12 of 12 candidates" look like a 100% context.

`initialFiles` and `expandedFiles` are reported separately because the relevance
budget applies to what relevance selected. Expansion is a separate budgeted
decision that may legitimately push the total higher. Both are derived from the
**final** file list, so the reported split cannot disagree with the files
actually emitted.

## Where a per-task manifest goes

`.uihub-agent/generated/CONTEXT_MANIFEST.json` is a **static template**, not
per-task state: an artifact that changed on every task could not be
freshness-checked. Write real output only where you ask for it:

```
npm run agent:context -- --manifest .tmp/ctx.json "<task>"
```
